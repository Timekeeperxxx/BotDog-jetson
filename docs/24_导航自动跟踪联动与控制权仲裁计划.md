# 导航自动跟踪联动与控制权仲裁计划

## 1. 目标

在机器狗执行雷达导航任务时，摄像头检测到陌生人后自动触发自动跟踪；自动跟踪期间暂停导航任务层，并剥夺导航速度控制权；定位、TF、ROS bridge、前端位姿订阅持续运行。自动跟踪结束后，系统确认没有用户干预和场景变化，再基于当前 TF 位姿重新规划到被中断的导航目标。

核心目标：

- 导航任务可被自动跟踪临时中断。
- 自动跟踪期间导航界面继续实时显示机器狗位置。
- 导航速度控制不能绕过后端仲裁直接控制机器狗。
- 自动跟踪结束后从机器狗当前位置重新规划，而不是回到旧路径状态。
- 用户手动停止、急停、切换场景、重启定位、建图等操作发生后，不自动恢复导航。

## 2. 当前关键判断

系统中已经具备以下基础能力：

- 自动跟踪服务：`backend/auto_track_service.py`
- AI 检测 Worker：`backend/workers_ai.py`
- 导航任务运行时：`backend/services_nav_task_runtime.py`
- ROS 导航桥：`backend/services_ros_nav.py`
- 导航状态：`backend/services_nav_state.py`
- 控制服务和仲裁雏形：`backend/control_service.py`、`backend/control_arbiter.py`

但要实现可靠联动，还需要补齐两个关键点：

1. 导航任务也要成为 AI 检测工作上下文。否则导航过程中摄像头检测到人，自动跟踪未必会处理该帧。
2. 导航速度控制必须进入统一控制网关。只暂停导航状态不等于真正剥夺导航控制权。

## 3. 总体架构

新增一个导航-自动跟踪协调器：

```text
AI Worker
  -> AutoTrackService 锁定陌生人
  -> NavAutoTrackCoordinator
      -> 暂停导航任务层
      -> 控制仲裁 owner 切到 AUTO_TRACK
      -> 保留定位 / TF / ROS bridge / 前端位姿广播

AutoTrackService 跟踪结束
  -> NavAutoTrackCoordinator
      -> 校验没有用户干预和场景变化
      -> 读取当前 TF / 当前导航状态
      -> 重新下发被中断目标
      -> 控制仲裁 owner 还给 NAVIGATION
```

## 4. 控制权仲裁原则

仲裁必须放在最后一跳速度控制链路上。也就是说，真实硬件只接受统一控制网关输出的速度或动作命令。

推荐控制权优先级：

```text
E_STOP
REMOTE_CONTROLLER / WEB_MANUAL
AUTO_TRACK
GUARD_MISSION
NAVIGATION
NONE
```

自动跟踪触发后：

- 导航任务层进入 `paused`。
- 控制仲裁 owner 切换为 `AUTO_TRACK`。
- 导航侧速度输入可以继续存在，但被统一控制网关丢弃。
- 自动跟踪命令由 `AutoTrackService -> ControlService -> RobotAdapter` 下发。

自动跟踪结束后：

- 协调器确认没有用户干预。
- 控制仲裁 owner 切回 `NAVIGATION`。
- 导航任务基于当前 TF 重新规划到原目标。

## 5. 导航控制链路改造

### 5.1 如果导航当前通过 ROS `/cmd_vel` 控制

推荐改为多输入、单输出的速度仲裁结构：

```text
导航后端 / p2p_move_base
  -> /botdog/nav/cmd_vel

自动跟踪
  -> /botdog/track/cmd_vel 或后端 ControlService

人工控制 / 急停
  -> 后端 ControlService

统一速度网关 / mux
  -> 真实 /cmd_vel 或 Unitree SDK
```

要求：

- 原导航节点不能直接发布到真实硬件消费的 `/cmd_vel`。
- 真实 `/cmd_vel` 或硬件 SDK 只接受仲裁后的输出。
- 自动跟踪期间，`/botdog/nav/cmd_vel` 的消息会被丢弃或不转发。

### 5.2 如果导航当前直接调用硬件 SDK

这种情况下你的后端无法单靠状态裁定导航控制权，必须改造。

可选方案：

- 将导航后端的硬件控制调用迁移到当前后端 `ControlService`。
- 或让导航后端只调用当前后端提供的导航控制 API。
- 或将导航速度输出改成中间 topic，由当前后端桥接到硬件。
- 如果短期无法改造，只能在自动跟踪时停止或挂起导航控制进程，但这不是最终方案。

验收标准：

- 导航模块不能绕过 `ControlArbiter` 直接控制机器狗。
- 把 owner 切到 `AUTO_TRACK` 后，导航侧继续发速度也不会影响机器狗。

## 6. 导航暂停策略

自动跟踪锁定陌生人时，不停止定位系统，只暂停导航任务执行。

应保留：

- ROS bridge 线程。
- TF 查询。
- 位姿订阅。
- `/nav_status` 订阅。
- 前端 `nav.robot_pose` / 导航状态广播。
- Super-LIO / 定位相关进程。

可暂停：

- 导航任务推进。
- 导航速度控制输出。
- 当前任务的目标执行状态。

后端行为：

- 发布 `/nav_start=false` 或调用等价暂停接口。
- `navigation_status.status` 更新为 `paused`。
- 记录被中断任务、目标点、场景、时间和中断原因。

## 7. 恢复与重新规划

自动跟踪结束条件：

- 陌生人离开关注区域。
- 目标连续丢失达到阈值。
- 自动跟踪被手动结束。
- 自动跟踪服务被禁用。

恢复前必须校验：

- 没有急停。
- 用户没有手动停止导航任务。
- 没有切换场景。
- 没有重启定位。
- 没有进入建图。
- 被中断的任务和目标仍然存在。
- 当前 TF / robot pose 可用。

恢复方式：

- 不复用自动跟踪前的旧路径。
- 使用当前 TF 位姿作为规划起点。
- 重新下发被中断的导航目标或恢复 `current_task.json` 对应任务。
- 发布 `/nav_start=true` 或重新调用单点/任务导航接口。

如果 global planner 本身以当前 TF 为起点，则只需要重新发布目标或启动任务；如果它会复用旧内部状态，则需要增加明确的 cancel/replan/reset 接口。

## 8. 后端模块改造清单

### 8.1 新增协调器

新增：

- `backend/nav_auto_track_coordinator.py`

职责：

- `pause_navigation_for_tracking(track_id)`
- `resume_navigation_after_tracking(reason)`
- `cancel_pending_resume(reason)`
- `is_navigation_context_active()`
- 记录被中断任务快照和场景版本。

### 8.2 接入自动跟踪状态机

修改：

- `backend/auto_track_service.py`

接入点：

- `DETECTING -> FOLLOWING` 锁定目标后暂停导航。
- `FOLLOWING/LOST -> STOPPED/IDLE` 后尝试恢复导航。
- `disable()`、`stop()`、人工接管时按原因决定是否恢复或取消。

### 8.3 接入 AI Worker

修改：

- `backend/workers_ai.py`

目标：

- 将“导航任务正在执行或被自动跟踪暂停”视为 AI 工作上下文。
- 导航中即使没有传统巡检任务，也持续处理 person 检测。

### 8.4 接入导航接口

修改：

- `backend/api/routes/nav.py`

接入点：

- 导航任务启动时可自动启用 auto-track。
- 用户手动停止导航时取消待恢复状态。
- 急停时取消待恢复状态。
- 重启定位、切换场景、开始建图时取消待恢复状态。

### 8.5 扩展控制仲裁

修改：

- `backend/control_arbiter.py`
- `backend/tracking_types.py`
- 可能需要新增 `NAVIGATION` owner。

目标：

- 支持导航速度控制来源。
- 支持 `AUTO_TRACK` 抢占 `NAVIGATION`。
- 支持人工和急停抢占一切自动控制。

## 9. 配置项

建议新增：

```text
NAV_AUTO_TRACK_DURING_NAV_ENABLED=true
NAV_AUTO_TRACK_AUTO_ENABLE=true
NAV_AUTO_TRACK_RESUME_TIMEOUT_S=3.0
NAV_AUTO_TRACK_REQUIRE_FRESH_TF=true
NAV_CONTROL_GATEWAY_ENABLED=true
```

含义：

- `NAV_AUTO_TRACK_DURING_NAV_ENABLED`：导航过程中是否允许陌生人触发自动跟踪。
- `NAV_AUTO_TRACK_AUTO_ENABLE`：启动导航任务时是否自动启用自动跟踪。
- `NAV_AUTO_TRACK_RESUME_TIMEOUT_S`：跟踪结束后等待 TF / 控制权恢复的最大时间。
- `NAV_AUTO_TRACK_REQUIRE_FRESH_TF`：恢复导航前是否必须有新鲜位姿。
- `NAV_CONTROL_GATEWAY_ENABLED`：是否强制导航速度经过统一控制网关。

## 10. 测试计划

单元测试：

- 导航中锁定陌生人后，发布 `/nav_start=false`，导航状态变为 `paused`。
- 自动跟踪结束后，发布 `/nav_start=true`，导航状态回到 `navigating`。
- 自动跟踪期间导航位姿广播不停止。
- 用户手动停止导航后，跟踪结束不恢复导航。
- 急停后，跟踪结束不恢复导航。
- 切换场景或重启定位后，跟踪结束不恢复旧任务。
- owner 为 `AUTO_TRACK` 时，导航速度输入被拒绝或丢弃。
- owner 为 `NAVIGATION` 时，导航速度输入允许转发。

现场联调：

- 启动导航任务，导航界面实时显示机器狗位置。
- 摄像头出现陌生人，自动跟踪触发，导航任务显示暂停。
- 跟踪期间导航界面位姿继续更新。
- 导航侧持续发速度时，机器狗仍只执行自动跟踪控制。
- 陌生人离开或目标丢失超时后，机器狗从当前位置重新规划回原目标。
- 跟踪期间点击急停或停止导航，跟踪结束后不会自动恢复导航。

## 11. 风险和前置条件

最大风险是导航后端当前可能绕过当前后端直接控制机器狗。只要这条直连路径存在，当前后端就无法真正剥夺导航控制权。

上线前必须确认：

- 真实硬件速度控制最终经过统一网关。
- 导航输出能被重映射到中间 topic 或后端 API。
- 自动跟踪和导航不会同时直接写真实 `/cmd_vel` 或 SDK。
- global planner 恢复时会使用当前 TF，而不是旧起点。

## 12. 推荐实施顺序

1. 梳理导航后端真实速度输出路径，确认是否直连硬件。
2. 先改造速度链路，让导航输出进入统一控制网关。
3. 扩展 `ControlArbiter`，加入 `NAVIGATION` owner。
4. 新增 `NavAutoTrackCoordinator`。
5. 接入 `AutoTrackService` 的锁定和结束状态。
6. 接入 `AIWorker`，让导航任务成为 AI 工作上下文。
7. 接入导航停止、急停、切场景、重启定位的取消恢复逻辑。
8. 添加单元测试和现场联调脚本。
9. 真机低速验证，再恢复正式速度参数。
